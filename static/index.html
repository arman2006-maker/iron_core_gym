Functional Dependencies & BCNF Normalization

Slide 5: eliminating partial & transitive dependencies

0NF
One flat 'gym register' sheet

Repeating phone numbers, mixed member/plan/session attributes.

1NF
Atomic values

Multi-valued phone attributes split out; primary keys assigned.

2NF
Full functional dependency

Plan & class details moved out of composite keys: Plan_ID → plan_name, duration, fee.

3NF
No transitive dependencies

Separated trainer_id → speciality and branch_id → city from session/member tables.

BCNF
Every determinant is a candidate key

Unique constraint on (room, session_start) → session_id prevents room double-booking.

Key Functional Dependencies: Member_ID → name, phone, email, DOB • Plan_ID → plan_name, duration, fee • Session_ID → class, trainer, start, capacity • (Member_ID, Session_ID) → status, booked_at • Payment_ID → amount, mode, date, sub_id
